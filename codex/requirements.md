# 중고거래 플랫폼 요구사항 분석

# 1. 서비스 개요

| 항목 | 내용 |
| --- | --- |
| 서비스명 | 중고거래 플랫폼 |
| 목적 | 사용자가 중고 상품을 등록하고, 검색하고, 다른 사용자와 소통하여 거래할 수 있는 웹서비스 |

| 1차 목표 | 중고거래가 가능한 최소 기능을 안정적으로 구현하는 것 |

| 사용자 유형 | 설명 | 주요 권한 |

| 구매자 | 상품을 구매하려는 회원 | 판매자와 채팅, 거래 요청, 송금 가능 |
| 관리자 | 플랫폼 운영자 | 회원 관리, 상품 관리, 신고 처리, 차단 처리 가능 |

# 3. 핵심 기능 요구사항

## 3.1 회원 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| USER-01 | 회원가입 | 상 | 사용자는 이메일, 비밀번호, 닉네임으로 가입할 수 있어야 한다. |
| USER-02 | 로그인 | 상 | 가입한 사용자는 이메일과 비밀번호로 로그인할 수 있어야 한다. |
| USER-03 | 로그아웃 | 상 | 로그인한 사용자는 로그아웃할 수 있어야 한다. |
| USER-04 | 내 정보 조회 | 상 | 사용자는 자신의 프로필 정보를 볼 수 있어야 한다. |
| USER-05 | 내 정보 수정 | 중 | 닉네임, 프로필 이미지, 소개글 등을 수정할 수 있어야 한다. |
| USER-06 | 회원 탈퇴 | 중 | 사용자는 계정을 탈퇴할 수 있어야 한다. |
| USER-07 | 사용자 신뢰도 표시 | 중 | 거래 횟수, 신고 이력 등을 기반으로 신뢰도를 표시할 수 있다. |

### 설명

회원 기능은 모든 기능의 기반이다.

상품 등록, 채팅, 신고, 거래 요청은 로그인한 사용자만 가능하게 해야 한다.

비회원은 상품을 볼 수는 있지만, 거래 관련 기능은 사용할 수 없도록 제한하는 것이 좋다.

## 3.2 상품 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| ITEM-01 | 상품 등록 | 상 | 판매자는 상품명, 가격, 설명, 이미지, 카테고리, 거래지역을 입력해 상품을 등록할 수 있어야 한다. |
| ITEM-02 | 상품 목록 조회 | 상 | 사용자는 등록된 상품 목록을 볼 수 있어야 한다. |
| ITEM-03 | 상품 상세 조회 | 상 | 사용자는 상품의 상세 정보, 판매자 정보, 거래 상태를 볼 수 있어야 한다. |
| ITEM-04 | 상품 수정 | 상 | 판매자는 자신이 등록한 상품 정보를 수정할 수 있어야 한다. |
| ITEM-05 | 상품 삭제 | 상 | 판매자는 자신이 등록한 상품을 삭제할 수 있어야 한다. |
| ITEM-06 | 상품 상태 변경 | 상 | 판매자는 상품 상태를 판매중, 예약중, 판매완료로 변경할 수 있어야 한다. |
| ITEM-07 | 상품 이미지 업로드 | 상 | 상품 등록 시 이미지를 1개 이상 업로드할 수 있어야 한다. |
| ITEM-08 | 카테고리 분류 | 중 | 상품은 전자기기, 의류, 가구 등 카테고리별로 분류되어야 한다. |
| ITEM-09 | 관심상품 등록 | 중 | 사용자는 관심 있는 상품을 찜할 수 있어야 한다. |

### 설명

중고거래 플랫폼에서 가장 중요한 기능은 상품 등록과 조회다.

1차 개발에서는 상품 등록, 목록 조회, 상세 조회, 수정, 삭제, 상태 변경까지는 반드시 포함해야 한다.

관심상품, 추천상품, 조회수 기능은 있으면 좋지만, 핵심 거래 기능보다 우선순위는 낮다.

## 3.3 검색 및 필터 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| SEARCH-01 | 키워드 검색 | 상 | 사용자는 상품명 또는 설명에 포함된 단어로 상품을 검색할 수 있어야 한다. |
| SEARCH-02 | 카테고리 필터 | 상 | 사용자는 카테고리별로 상품을 필터링할 수 있어야 한다. |
| SEARCH-03 | 가격 필터 | 중 | 사용자는 최소 가격, 최대 가격을 기준으로 상품을 검색할 수 있어야 한다. |
| SEARCH-04 | 지역 필터 | 중 | 사용자는 거래 지역을 기준으로 상품을 검색할 수 있어야 한다. |
| SEARCH-05 | 정렬 기능 | 중 | 최신순, 낮은 가격순, 높은 가격순으로 정렬할 수 있어야 한다. |

### 설명

검색 기능은 상품 수가 많아질수록 중요해진다.

초기에는 **키워드 검색 + 카테고리 필터 + 최신순 정렬** 정도만 있어도 충분하다.

가격 필터, 지역 필터는 2차 기능으로 추가해도 된다.

## 3.4 사용자 간 소통 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| CHAT-01 | 채팅방 생성 | 상 | 구매자는 상품 상세 페이지에서 판매자에게 채팅을 시작할 수 있어야 한다. |
| CHAT-02 | 메시지 전송 | 상 | 사용자는 채팅방에서 메시지를 주고받을 수 있어야 한다. |
| CHAT-03 | 채팅 목록 조회 | 상 | 사용자는 자신이 참여 중인 채팅방 목록을 볼 수 있어야 한다. |
| CHAT-04 | 채팅 내역 조회 | 상 | 사용자는 기존 대화 내용을 볼 수 있어야 한다. |
| CHAT-05 | 읽음 여부 표시 | 하 | 메시지를 상대방이 읽었는지 확인할 수 있다. |
| CHAT-06 | 이미지 전송 | 하 | 채팅에서 이미지를 보낼 수 있다. |

### 설명

채팅은 거래 성사에 직접적으로 연결되는 기능이다.

1차 구현에서는 실시간 채팅이 아니어도 된다.

초기 버전에서는 다음 방식으로 구현할 수 있다.

| 방식 | 설명 |
| --- | --- |
| 일반 메시지 방식 | 사용자가 새로고침하거나 일정 시간마다 메시지를 불러옴 |
| 실시간 채팅 방식 | WebSocket 등을 사용해 즉시 메시지가 표시됨 |

처음부터 WebSocket 기반 실시간 채팅을 만들면 복잡도가 올라간다.

초기에는 일반 메시지 방식으로 만들고, 이후 실시간 채팅으로 확장하는 것이 현실적이다.

## 3.5 신고 및 차단 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| REPORT-01 | 상품 신고 | 상 | 사용자는 사기 의심, 금지 상품, 허위 정보 등의 이유로 상품을 신고할 수 있어야 한다. |
| REPORT-02 | 사용자 신고 | 상 | 사용자는 악성 사용자, 욕설, 사기 의심 사용자를 신고할 수 있어야 한다. |
| REPORT-03 | 신고 내역 저장 | 상 | 신고 사유, 신고자, 신고 대상, 신고 시간을 저장해야 한다. |
| BLOCK-01 | 사용자 차단 | 중 | 사용자는 특정 사용자를 차단할 수 있어야 한다. |
| BLOCK-02 | 차단 사용자와 채팅 제한 | 중 | 차단한 사용자와는 채팅이 불가능해야 한다. |
| ADMIN-REPORT-01 | 관리자 신고 처리 | 상 | 관리자는 신고 내역을 확인하고 조치할 수 있어야 한다. |

### 설명

중고거래 플랫폼은 사기, 허위 매물, 욕설, 금지 물품 문제가 자주 발생한다.

따라서 신고 기능은 선택 기능이 아니라 필수 기능에 가깝다.

다만 자동 차단은 위험할 수 있다.

초기에는 신고가 접수되면 관리자가 직접 확인하고 처리하는 방식이 적절하다.

## 3.6 송금 및 결제 기능

| ID | 요구사항 | 우선순위 | 설명 |
| --- | --- | --- | --- |
| PAY-01 | 거래 요청 | 상 | 구매자는 상품에 대해 거래 요청을 보낼 수 있어야 한다. |
| PAY-02 | 판매자 거래 수락 | 상 | 판매자는 구매자의 거래 요청을 수락하거나 거절할 수 있어야 한다. |
| PAY-03 | 송금 또는 결제 요청 | 중 | 구매자는 거래가 확정된 상품에 대해 결제할 수 있어야 한다. |
| PAY-04 | 결제 상태 관리 | 중 | 결제대기, 결제완료, 거래완료, 취소 등의 상태를 관리해야 한다. |
| PAY-05 | 거래 내역 조회 | 중 | 사용자는 자신이 구매하거나 판매한 거래 내역을 볼 수 있어야 한다. |
| PAY-06 | 환불 또는 취소 처리 | 하 | 거래 취소 시 환불 처리가 가능해야 한다. |

### 설명

하지만 실제 서비스에서 사용자 간 직접 송금 기능은 보안, 법적 문제, 정산 문제, 환불 문제 때문에 복잡하다.

따라서 초기 요구사항에서는 “송금”을 바로 구현하기보다는 다음처럼 나누는 것이 좋다.

| 단계 | 방식 |
| --- | --- |
| 1차 구현 | 거래 요청, 거래 수락, 거래 상태 관리 |
| 2차 구현 | 외부 결제 API 연동 |
| 3차 구현 | 안전결제, 에스크로, 환불 처리 |

처음부터 송금 기능을 넣으면 서비스 난이도가 크게 올라간다.

MVP에서는 거래 요청과 거래 상태 관리까지만 구현해도 충분하다.

“관리자가 플랫폼의 모든 요소를 관리할 수 있어야 한다”는 요구사항은 너무 넓다.

구체적으로는 다음 요소를 관리해야 한다.

| 관리 대상 | 관리 내용 |
| --- | --- |
| 회원 | 조회, 정지, 해제, 탈퇴 처리 |
| 상품 | 조회, 삭제, 숨김, 신고 상품 확인 |
| 신고 | 신고 사유 확인, 처리 상태 변경 |
| 거래 | 거래 상태 확인, 문제 거래 확인 |
| 채팅 | 필요 시 신고된 채팅 내용 확인 |
| 공지 | 서비스 공지 등록 및 수정 |

# 4. 주요 업무 흐름

## 4.1 상품 등록 흐름

| 단계 | 설명 |
| --- | --- |
| 1 | 사용자가 로그인한다. |
| 2 | 상품 등록 페이지로 이동한다. |
| 3 | 상품명, 가격, 설명, 이미지, 카테고리, 지역을 입력한다. |
| 4 | 등록 버튼을 누른다. |
| 5 | 시스템은 입력값을 검증한다. |
| 6 | 상품이 등록된다. |
| 7 | 상품 목록과 상세 페이지에서 해당 상품을 볼 수 있다. |

---

## 4.2 거래 진행 흐름

| 단계 | 설명 |
| --- | --- |
| 1 | 구매자가 상품을 검색한다. |
| 2 | 상품 상세 페이지를 확인한다. |
| 3 | 판매자에게 채팅을 보낸다. |
| 4 | 판매자와 구매자가 거래 조건을 협의한다. |
| 5 | 구매자가 거래 요청을 보낸다. |
| 6 | 판매자가 거래 요청을 수락한다. |
| 7 | 상품 상태가 예약중 또는 판매완료로 변경된다. |
| 8 | 거래 내역이 저장된다. |

---

## 4.3 신고 처리 흐름

| 단계 | 설명 |
| --- | --- |
| 1 | 사용자가 상품 또는 사용자를 신고한다. |
| 2 | 신고 사유를 선택하거나 입력한다. |
| 3 | 신고 내역이 저장된다. |

| 7 | 신고 처리 상태가 변경된다. |

# 9. 요구사항 분석 결론

이 중고거래 플랫폼의 핵심은 다음 4가지다.

| 핵심 영역 | 설명 |
| --- | --- |
| 상품 | 사용자가 상품을 등록하고 다른 사용자가 볼 수 있어야 한다. |
| 소통 | 구매자와 판매자가 거래 전 대화할 수 있어야 한다. |
| 안전 | 신고, 차단, 관리자 조치로 악성 사용자와 악성 상품을 관리해야 한다. |
| 거래 | 상품 상태와 거래 상태를 명확히 관리해야 한다. |

현재 단계에서는 **실제 송금 기능보다 거래 요청과 거래 상태 관리가 우선**이다.

송금 기능은 외부 결제 API, 환불 정책, 보안 처리가 필요하므로 2차 개발로 분리하는 것이 좋다.

따라서 1차 목표는 다음과 같이 잡는 것이 적절하다.

> 사용자가 가입하고, 상품을 등록하고, 검색하고, 채팅으로 거래를 협의하고, 문제가 생기면 신고할 수 있으며, 관리자가 이를 관리할 수 있는 중고거래 플랫폼을 만든다.
